# Qadam — Qiwi na abaya

Фундамент MVP платформы бизнес-задач для студенческих команд.
Next.js App Router, TypeScript, Tailwind CSS, lucide-react, Prisma 6 и локальная SQLite.

## Быстрый старт

Требуется Node.js 22.18+ и npm. Все команды выполняются в корне проекта.

```sh
npm ci
```

Скопируйте `.env.example` в `.env` (PowerShell: `Copy-Item .env.example .env`; macOS/Linux: `cp .env.example .env`).

```sh
npm run db:setup
npm run dev
```

Откройте http://localhost:3000. Главная страница читает задачи, команды и статистику из БД при каждом запросе.

## Данные и модели

- `Business`: бизнес, контактное лицо и контакт.
- `Team`: профиль команды; interests, skills, technologies — JSON-массивы строк (SQLite не поддерживает Prisma scalar lists).
- `Task`: исходное описание, все поля карточки, JSON-массив skills, рейтинг, уровень, статус, бизнес-владелец, даты. Пустые поля допустимы для слабого черновика. `confirmedAt` и `publishedAt` сохраняют факт ручного подтверждения и публикации.
- `Proposal`: идея, план, срок, ссылка и статус предложения; не более одного предложения команды на задачу. Принятие не назначает команду автоматически и не меняет другие предложения.
- `Clarification`: упорядоченные вопросы и сохранённые ответы для будущего мастера.

Статусы задачи: DRAFT, PUBLISHED, IN_PROGRESS, COMPLETED. Статусы предложения: PENDING, ACCEPTED, REJECTED. Статус публикации и уровень готовности независимы.

Seed добавляет вымышленный Qadam Market, пять реалистичных команд, пять публикаций с рейтингами 30/55/70/90/100, пять черновиков, пять ожидающих предложений и три вопроса к черновику. Контакты `.example` и ссылки `example.com/prototypes/...` — обозначенные демонстрационные данные, не реальные прототипы. Низкорейтинговая публикация также имеет предложение.

Seed транзакционный, повторный запуск не удаляет записи и не перезаписывает пользовательские изменения. SQLite хранится в `prisma/dev.db`: путь `file:./dev.db` считается относительно Prisma-схемы. Перезапуск сервера не стирает данные. `.env`, БД и её служебные файлы исключены из Git. Для переноса данных скопируйте БД при остановленном приложении. Для хакатона запускайте приложение на машине с постоянным диском.

## Рейтинг

Единая функция `src/lib/scoring.ts` используется seed, редактором и серверными операциями сохранения карточки. Контекст и потребность дают по 10 баллов; данные — 20; результат и критерии — по 15; ограничения, пользователи и связь с бизнесом — по 10. Пробелы не считаются заполнением. Это прозрачный рейтинг заполненности: он не проверяет истинность или содержательное качество текста. Из исходного описания и профиля бизнеса сведения не додумываются.

Уровни: 0–39 Черновик; 40–69 Рабочая; 70–89 Готовая; 90–100 Приоритетная. Функция возвращает баллы по категориям, недостающие поля и подсказки. Будущие операции записи должны обновлять поля, score и readinessLevel вместе. Enum-поля проверяет Prisma Client; SQLite сама не ограничивает их значения. Прямые SQL-записи должны соблюдать те же правила.

Перед миграцией npm автоматически открывает SQLite через Prisma Client, создавая отсутствующий файл без изменения существующих данных. В зависимостях зафиксирован override `deepmerge-ts` 8 для устранения GHSA-ggr8-5vv4-36mx в транзитивной зависимости Prisma CLI.

## Границы текущего этапа

Реализованы база, seed, правила рейтинга и SaaS-оболочка: dashboard бизнеса, мои задачи, создание и сохранение черновика, каталог с поиском/фильтрами/сортировкой, карточка задачи с детализацией баллов, просмотр предложений, рекомендации по совпадениям с профилем, мои отклики и редактирование профиля команды. Данные берутся из SQLite. Реализован четырёхшаговый конструктор с fallback-анализом, редактированием и ручной публикацией карточки. OpenAI помогает анализировать и структурировать задачи; без API работает deterministic fallback. Отправка предложений командами реализована; принятие и отклонение бизнесом — следующий этап.

## Пространства бизнеса и команды

Корень перенаправляет в `/business` или `/catalog` по роли. Переключатель Бизнес / Команда сохраняет роль в HttpOnly cookie на 30 дней. На `/team/profile` можно выбрать любую из демонстрационных команд; выбор также сохраняется. Это явный деморежим без аутентификации, не граница безопасности для публичного production-сервиса. Серверные операции создания черновика и редактирования профиля проверяют выбранную роль. Черновики бизнеса не доступны в пространстве команды.

Dashboard считает все задачи выбранного бизнеса, опубликованные, средний score по всем его задачам (включая черновики), предложения и распределение по уровням. Рекомендации используют точные совпадения отрасли/навыков с интересами, навыками и технологиями команды; это не автоматический выбор исполнителя.

На desktop — sidebar, на мобильном — меню в native dialog. Диалоги поддерживают Escape и возврат фокуса. Есть skip-link, клавиатурный focus, aria-current, текстовые уровни готовности, progress meters, reduced-motion, skeleton загрузки, empty/error states и toast после сохранения.

## Конструктор бизнес-задачи

`/business/tasks/new` — четыре шага: описание → уточнения → карточка → подтверждение. При первом сохранении создаётся DRAFT, ссылка получает `?task=<id>`. Из «Моих задач» и карточки черновика можно продолжить конструктор.

Описание, ответы, все редактируемые поля и шаг сохраняются в SQLite. Автосохранение — через 750 мс после ввода; переходы вперёд/назад сначала сохраняют данные. Локальная резервная копия защищает ввод при перезагрузке до завершения сохранения; восстановленный текст нужно сохранить кнопкой. Запросы клиента идут последовательно, ревизия черновика предотвращает тихую перезапись из другой вкладки. Не закрывайте страницу до сообщения «Все изменения сохранены», если браузер запрещает localStorage.

Поле Task.wizardState хранит текущий шаг, исходный анализ, активные вопросы, начальный score и список вручную изменённых полей; wizardRevision защищает конкурентные записи. Сами вопросы/ответы хранятся в Clarification. Миграция добавляет поля без удаления существующих данных.

`src/lib/ai/server.ts` — серверные операции AI; `src/lib/task-assistant.ts` — deterministic fallback: буквальные фрагменты исходного текста, явные подписи полей и консервативные языковые правила. Вопросы задаются по отсутствующим областям; для подробного брифа задаются дополнительные вопросы о границах, приёмке и приоритетах. Неизвестное не заполняется выдуманными фактами. Ответ «не знаю» не приносит баллы. Это эвристика заполненности, а не полноценное понимание естественного языка.

При формировании карточки используются исходный текст и сохранённые ответы. Ручные правки, включая намеренно очищенные поля, сохраняются при повторном проходе. При изменении описания вопросы обновляются, прежние ответы доступны в разделе «Ранее сохранённые ответы». Ошибка или некорректный ответ провайдера переводит анализ на fallback.

Публикация — отдельная серверная операция: проверяются роль, владелец, статус DRAFT, ревизия, актуальность анализа, наличие названия, шаг предварительного просмотра и явное подтверждение. Только затем одной транзакцией выставляются PUBLISHED, confirmedAt и publishedAt. Рейтинг не ограничивает публикацию. Команды автоматически не назначаются.

Проверки: `npm test` проверяет рейтинг, слабые/подробные описания, отсутствие повторных вопросов по явным данным, буквальное формирование, сохранение ручных правок и fallback при сбое провайдера. Сквозной проход в браузере: слабое описание → 6 вопросов → ответы → рейтинг 20→100 → ручные правки → возврат/reload → preview остаётся DRAFT → подтверждение → каталог команды. Отдельно проверена публикация задачи с 0 баллов.


### Правила scoring
Чистый модуль возвращает `total`, `level`, `categories` (key, label, score, maxScore, missing) и `suggestions`. Для совместимости сохранены score/readinessLevel/breakdown. Код уровня 40–69: WORKABLE.

Пустые поля, пунктуация и ответы «не знаю», «не определено», «нет данных» дают 0. Краткое значение даёт половину веса. Минимум четыре различных слова длиной от двух символов и 20 символов без пробелов дают полный вес. В контексте и потребности каждый из двух блоков оценивается отдельно из 10. Итог категории округляется вниз (половина от 15 = 7). Это простой открытый индикатор заполненности, а не проверка достоверности или литературного качества. Указанное отсутствие бюджета или ограничений может быть полезной информацией.

После обновления существующей базы: `npm run db:deploy`, `npm run db:generate`, `npm run db:rescore`. Последняя команда пересчитывает все задачи и исходный рейтинг конструктора, увеличивает ревизию против записи из устаревшей вкладки, не меняет статусы публикаций и предложения. Перезапустите приложение и обновите открытый конструктор. Seed не перезаписывает существующие записи.

Unit tests проверяют 0/39/40/69/70/89/90/100, веса, частичное заполнение, неизвестные значения, удаление данных, повторение слов, независимость от исходного текста и чистоту функции. В редакторе рейтинг обновляется сразу, сохранение происходит на сервере по той же формуле; анимация отключается при prefers-reduced-motion. Низкий рейтинг не ограничивает публикацию и видимость в каталоге.


### AI: OpenAI и заменяемый провайдер

По умолчанию используется **OpenAI Responses API**, модель `gpt-4o-mini`. `AI_MODEL` меняет модель без правки кода (нужна поддержка Structured Outputs). Формат запроса соответствует [официальной документации OpenAI](https://developers.openai.com/api/docs/guides/structured-outputs): `text.format.type=json_schema`, `strict=true`. Запросы идут с сервера прямо на `https://api.openai.com/v1/responses`, `store:false`, без инструментов и выбора команд.

В локальном `.env`:

```dotenv
AI_API_KEY=
AI_MODEL=gpt-4o-mini
```

Ключ не имеет префикса NEXT_PUBLIC, не записывается в БД, клиентские props или логи. `.env` исключён из Git; `.env.example` не содержит секретов. После изменения env перезапустите сервер. В приложении env читает только `ai/server.ts`, защищённый импортом `server-only`. Полный текст задачи и ответы передаются выбранному AI-провайдеру; не вводите чувствительные сведения.

**Замена провайдера.** Реализуйте `AIProvider` из `src/lib/ai/service.ts` и подставьте его в фабрику `server.ts`. UI и server actions зависят от двух операций сервиса, а не от SDK. HTTP-адаптер находится в `ai/openai.ts`; схемы Zod и их JSON Schema — в `ai/schemas.ts`. Отдельный SDK не требуется: используется серверный fetch.

**Вход / выход:**

```ts
analyzeDraft(rawDescription: string, existingData: Partial<TaskCardInput>)
// data: {
//   missingFields: ["users", "dataMaterials", ...],
//   questions: [{key: "users", question: "Какая роль будет пользоваться результатом?"}, ...] // минимум 3
// }
structureTask(rawDescription: string, answers: {key: string; question: string; answer: string}[])
// data: {title, industry, context, need, users, dataMaterials,
//        expectedResult, successCriteria, constraints, businessContact, skills}
// Каждое поле карточки — строка. Неизвестное: ""; skills: названия через запятую.
// Обе операции возвращают {data, mode: "openai" | "fallback", reason?}.
```

AI-вход — JSON с названием операции и указанными аргументами. Анализ дополнительно получает `candidateQuestions` с допустимыми ключами ещё не отвеченных вопросов. Для полного брифа предлагаются дополнительные уточнения. Внутренний AI-ответ при структурировании имеет вид `{evidence: {...11 полей-цитат}, card: {...11 полей}}`: сначала выбираются цитаты, затем формулировки. Сервис удаляет evidence из публичного результата. Ни вопросы, ни метаданные сами по себе не являются доказательством фактов.

**Prompt.** Полный prompt экспортируется как `AI_PROMPT` в `ai/openai.ts`. Он требует: только явно сообщённые факты; неизвестные поля пустые; улучшать ясность без изменения смысла; минимум три конкретных неповторяющихся вопроса; не запрашивать личные или чувствительные данные; использовать роли и рабочий формат связи; не выбирать команду, не назначать исполнителя, не публиковать и не выставлять рейтинг. Входные строки трактуются как недоверенные данные, а не инструкции. Каждое непустое поле должно опираться на дословный фрагмент исходного описания или ответа.

**Валидация и fallback.** Strict Zod schemas проверяют типы, обязательные поля, отсутствие лишних полей, длины и минимум три вопроса. Дополнительно проверяются уникальность ключей/вопросов, допустимые вопросы, отсутствие повторного запроса уже известного поля и дословная принадлежность цитат исходному описанию или ответам. Проверка цитат уменьшает риск выдуманных сведений, но не доказывает смысловую корректность — бизнес редактирует и подтверждает все поля. Невалидный ответ целиком отбрасывается, не сохраняется и не показывается пользователю.

Нет ключа (`no_key`), API/сеть недоступны (`unavailable`), превышено **20 секунд** (`timeout`), невалидный JSON/схема, отказ модели или неполный ответ (`invalid_response`) → автоматический deterministic fallback для той же операции. Таймаут ограничивает и заменяемый провайдер; fetch получает AbortSignal. Автоматических повторных платных запросов нет. Fallback использует буквальные сведения из описания и ответы, поддерживает весь сценарий, не выдумывает неизвестное. Его сообщения объясняют режим без сырых ошибок API. Структурирование не перезаписывает поля, вручную изменённые бизнесом, включая намеренно пустые.

**Проверка:** `npm test` не обращается к API: успешные ответы, ошибки HTTP, refusal, невалидный JSON, схемы, неподтверждённые цитаты и таймаут проверяются подставным провайдером/transport. `npm run ai:check:offline` проверяет обе операции без ключа даже при заполненном `.env`. `npm run ai:check` делает два реальных запроса с синтетическим описанием магазина и заканчивается ошибкой, если настроенный API не отработал обе операции. Скрипт выводит только режим, причины fallback, число вопросов и названия заполненных полей, без ключа, заголовков и сырых ответов API. Реальные запросы расходуют квоту API.


### Общий каталог и отклик

`/tasks` — общий каталог только PUBLISHED задач из SQLite. `/catalog` перенаправляет на новый адрес, сохраняя query-параметры. Фильтры в URL: `q` (название/описание), `industry`, `level` (DRAFT/WORKABLE/READY/PRIORITY), `skill` (точный навык без учёта регистра); `sort=newest` или `sort=score`. Фильтры работают совместно. Дата — publishedAt, при её отсутствии createdAt; редактирование не поднимает задачу как новую. Равный рейтинг разрешается датой, затем id. Рейтинг 0–39 не скрывает опубликованную задачу: уровень готовности DRAFT отличается от статуса неопубликованного черновика DRAFT. Выбор фильтра готовности намеренно сужает выдачу.

Для локального MVP запрос получает опубликованные карточки вместе с бизнесом и количеством откликов; чистая функция `src/lib/catalog.ts` фильтрует и сортирует небольшую выборку. Карточки показывают бизнес, отрасль, описание, навыки, рейтинг, уровень, дату и число откликов. У каталога есть skeleton, пустые состояния, reset фильтров, error boundary с повтором и отдельное состояние недоступной задачи.

`/tasks/[id]` содержит полное описание и breakdown рейтинга. Команда открывает «Предложить решение», заполняет идею, план, срок и необязательную HTTP(S)-ссылку на прототип. Server action повторно проверяет роль, опубликованный статус и поля; отклик сохраняется как PENDING. Unique(taskId, teamId) исключает дубли, включая одновременные отправки. Проверки рейтинга для отклика нет. Ошибка сохраняет текст в форме, успешная отправка открывает «Мои отклики» с уведомлением. Данные немедленно доступны бизнесу. Автоматическое назначение команды отсутствует; интерфейс принятия/отклонения будет следующим этапом. Демороли не заменяют production-аутентификацию.
